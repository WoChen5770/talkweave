## Context

动机与功能范围见 `proposal.md`。本设计需要显式处理跨模块运行状态、安全边界和数据模型变化，因此不跳过设计文档。

当前实现是 Java 21 / Spring Boot 单进程，管理 Web 未启用，只有容器内回环健康端点。`channel_state` 用 `CHECK (slot = 1)` 限制一套连接；`ConversationRepository.Binding` 来自固定配置；`AssistantRuntime` 有一条接收循环和一条消费循环；所有登录材料写到同一个 `login/`。历史虽已按机器人和用户查询，但不能据此宣称整套运行时支持多用户。

`IdentityVerifier` 依靠本地一次性口令取得候选发送者后，仍要求人工修改配置。登录返回的 `ilink_user_id` 与消息的 `from_user_id` 尚无经过本项目验证的通用等价关系。`CompatibleChatClient` 当前只返回文本和截断状态，未保留服务端用量；`ContextBudget` 使用 UTF-8 字节启发式限额，不是精确 token 计数。

当前主规格目录为空，已有单用户 change 尚未归档。本轮以新 change 描述下一版本，不修改旧 change，不把其中单用户/手工授权/无 Web 的约束与本轮范围同时当作生效规格。后续归档需要显式协调这组替换关系。

## Goals / Non-Goals

**Goals:**
- 让管理控制面与各用户运行面解耦；单容器内用户之间隔离，用户内按序处理。
- 把“扫码者成为主人”建立在验证过的身份关联上；先规定失败关闭的边界，再验证外部协议，禁止静默退回首消息认领。
- 将会话归属、授权版本和用量归属固化到持久事件，保证延迟、重启、热更新及重绑不串数据。
- 保持中转站兼容性；缓存是可观测优化，不是正确性依赖，不承诺命中率或金额收益。

**Non-Goals:**
- 不接管微信全部好友或群聊，不增加工具执行、媒体理解、知识库和 Agent 编排。
- 不提供聊天正文管理、每用户模型配置、公开邀请页、自助注册、多管理员 RBAC 或收费账单。
- 不实现特定模型厂商的显式缓存产品；只保留清晰适配边界，不显示尚未实现的“专用缓存已开启”。
- 不迁移或自动删除当前账号数据，不同时保留一条可绕过管理授权的旧单用户运行入口。
- 不提供多副本共享数据库、跨节点调度或容器级的每用户物理隔离；第一版目标是同一受信任宿主机上的小规模使用。

## Decisions

### 1. 一个应用进程，独立控制面与连接运行面

加入 Spring Boot Web/Security，同源提供中文静态页面和 `/api/admin/**`；页面用轻量 JavaScript，不引入必须独立部署的前端服务。`RuntimeManager` 按有效绑定管理 `ChannelRuntime`，后者独立持有微信客户端、登录/重连状态、接收循环和取消句柄。管理服务、共享调度器和模型客户端池不能由某一个用户的关闭逻辑释放。

```text
管理员浏览器 ──认证/CSRF── 管理 API ── 用户/任务/设置/审计
                              │
                              └── RuntimeManager
                                   ├── A 的微信连接 → A 的持久事件 ─┐
                                   └── B 的微信连接 → B 的持久事件 ─┤
                                                                  ▼
                                                       公平、有界模型调度
                                                                  │
                                                       各自授权历史/回复
```

**替代方案：** 为每人创建一个容器虽能更强隔离，但需要管理容器生命周期、更多资源，甚至诱导挂载 Docker socket；本版不采用。单一全局接收循环不能正确维护多套 token/游标，也不采用。

### 2. 身份验证作为开通前置能力，而非可跳过的 TODO

先做协议验证任务，定义 `ScannerIdentityResolver` 边界：输入已确认登录结果与可信协议上下文，输出带身份命名空间的稳定账号标识、机器人标识、可用于入站授权的 sender 标识，以及验证依据版本；无法证明关系则返回 `UNSUPPORTED` 或 `UNVERIFIED`，不输出猜测的 owner。

可接受依据是可靠的协议保证或可信身份映射机制，并用至少两个授权账号验证实现与协议范围吻合；仅看到两个字符串相等、扫码状态为 `SCANNED` 或收到第一条消息都不够。实际联调必须记录两套连接是否并存、同号重扫是否复用机器人或撤销旧 token。验证过程允许操作者发送普通测试消息来核对身份，不得把该测试步骤固化成最终用户必须发送绑定口令。

该能力默认不视为已支持；真正的自动激活路径只对有证据支持的协议范围开放。合成适配仅用于测试，不作为生产绕过开关。如果无法找到可靠映射或多连接不成立，停止宣称自动开通已交付，保留失败关闭，向用户报告需要重新讨论接入方案；不擅自改成首消息绑定或手工口令产品流程。其他独立管理页/存储开发可以推进，但真实开通任务和端到端验收保持未完成。

**替代方案：** 直接 `ownerId = scanUserId` 或“第一个发言者即主人”实现简单但没有授权依据，排除。既有口令流程更稳妥但不满足本轮明确选择的体验，不作为隐式降级。

### 3. 二维码是管理员发放的有范围的一次性邀请

每个 `binding_attempt` 绑定内部 `user_id`、任务 ID、尝试版本、用户授权 epoch、目标模式（首次绑定/同身份认证/身份更换）、过期时间和消费状态。初始本地有效期沿用 8 分钟；若协议提供更短有效期，取两者较短值。二维码/配对码仅当前有效任务可用，不出现在 URL 查询、普通日志、审计或持久浏览器存储中。

任务阶段：`REQUESTING_QR → QR_READY → SCANNED/NEED_PAIRING → VERIFYING_IDENTITY → SUCCEEDED`，终止分支为 `EXPIRED / CANCELLED / CONFLICT / IDENTITY_UNVERIFIED / FAILED`。只以确认登录及身份验证成功进入激活事务；`SCANNED` 不代表授权完成。页面可轮询脱敏状态，单独认证的图片接口返回 `Cache-Control: no-store`；不将 `data/` 或临时文件目录映射为静态资源。登录材料使用任务独立的受保护临时目录，成功/取消/过期清理；服务重启取消未完成任务，不能恢复旧二维码认领。

刷新时先原子失效旧尝试，再申请新码。提交最终结果使用任务版本、用户状态和 epoch 的 compare-and-set；同时校验机器人及可靠账号身份唯一性；重复成功回调幂等。两个浏览器标签页、停用与扫码并发以及迟到响应都不能改变目标用户。

管理员备注仅为标签，不证明扫码者现实身份；持有码者扫码可以获得对应名额，这是本轮接受的邀请信任模型。第一版不做可转发公开绑定页。

**替代方案：** 复用全局 `login/` 会使同时绑定覆盖材料；二维码状态中直接返回 token 会扩大浏览器暴露面；均排除。

### 4. 新数据库布局与不可混用的范围键

使用新目录中的 `talkweave-admin.sqlite` 和明确的多用户应用布局标记；启动写入前检测旧 `assistant.sqlite`、已有旧运行布局及未知 schema，发现时拒绝操作并要求新目录。不能仅换数据库文件名就在旧目录旁悄悄初始化。

主要实体：

| 实体 | 关键字段与职责 |
| --- | --- |
| `administrator` | 唯一管理员、密码哈希、账户时间；不存可逆密码 |
| `app_user` | 内部用户 ID、备注、启用状态、`auth_epoch` |
| `binding` | 用户、身份范围版本、验证过的账号/sender、bot、状态；保留失效版本供审计和历史归属 |
| `channel_session` | binding、token、origin、连接 generation、cursor、有效状态；只存服务端 |
| `binding_attempt` | 用户、尝试版本、状态、模式、期限、发起 epoch；不把明文二维码内容塞进普通状态行 |
| `conversation` | 用户、binding 版本、当前标记、创建/结束时间、最后有效用户消息时间 |
| `inbound_event / turn` | 用户、binding、generation、auth epoch、机器人消息去重键、接收序号/时间、固定 conversation ID、处理与投递状态 |
| `model_configuration` | 全局设置及不可变版本、受保护 Key；非秘密版本标识用于请求归属 |
| `model_attempt / model_usage` | 调用尝试 ID、原用户/绑定/会话/模型版本、结果、可空用量、数据完整性 |
| `admin_setting / audit_event` | 全局超时与版本、脱敏操作事件 |

在外键、唯一约束和所有 repository 查询中同时携带用户与绑定范围，不只靠前端传 `userId`。对活动绑定建立 bot 唯一约束；账号唯一键使用 resolver 证明的身份命名空间与稳定 ID，不能把仅 bot 内有效的 sender 当作全局微信账号。消息去重键继续以可信 bot 范围和稳定 message ID 为基础，不把重新登录代次加入键来绕过去重。

继续 SQLite WAL 和短事务，事务内禁止外部网络调用。私有目录 `0700`、数据库及凭据材料 `0600`；不声称这些权限能防御宿主机 root 或数据库管理员，也不承诺本版透明加密存储。

**替代方案：** 一用户一个 SQLite 文件易形成文件生命周期与跨用户管理事务问题；小规模首版采用单库强范围约束，保留未来分库空间。旧单用户 schema 就地扩展并迁移增加未经请求的数据风险，排除。

### 5. 登录代次、身份更换和停用采用不同版本

`binding_version` 表示身份/历史授权范围，`generation` 表示某绑定内的连接凭据代次，`auth_epoch` 表示用户授权撤销序号。每个已接受任务保存对应快照。停用、明确重绑或失效权限会推进 epoch 并阻止新工作，尽力取消相关在途调用；发送、辅助微信操作和历史加载前重新检查快照。即使用户在旧请求完成前被恢复，旧 epoch 请求仍不能复活。

同身份重新认证仅替换连接凭据/代次，不把别人变成主人，保留同身份历史并继续按会话超时判断。管理员明确确认身份更换时先撤销旧运行授权，再启动新绑定任务；取消或失败不自动恢复已撤销的旧连接。新身份激活时使用新 binding 版本和新会话，不能读取旧历史。历史删除或转移不在本版范围。

已经发出的远端请求无法可靠撤回。已知用量仍保存；已发出的微信消息若结果不明确保持 `DELIVERY_UNKNOWN`，不能伪装成未发送。已完成且范围仍有效的消息可恢复；处理中的模型工作重启后保守中断，不自动再次计费。

**替代方案：** 只检查一个 `enabled` 布尔值无法防止“停用后恢复”间隙的旧任务发送；只用连接 generation 又不能表达历史归属，故采用分层版本。

### 6. 用户内串行，用户间公平的有界执行

接收端按 binding 独立轮询/退避；持久化事件后由共享调度器按有待处理工作的用户轮转领取。每个用户最多一个业务处理任务，默认全局模型并发上限 4；默认每用户待处理上限 1000，总待处理上限 10000。上述运行资源上限使用服务配置，第一版不增加管理端复杂配额页面。它们是初始工程默认值，不是性能承诺。

每用户积压限制只暂停该用户新增接收；全局上限、数据库不可用或低磁盘可暂停所有新增接收，但不丢弃已接受事件。模型客户端和连接池共用不可变模型配置版本，引用计数或等效租约管理在途请求，切换配置不立即关闭仍在使用的客户端。单用户关闭不能 shutdown 共享模型执行器。

**替代方案：** 全局单 worker 会被一个慢用户阻塞；无限制线程/请求会耗尽内存或中转额度。独立虚拟线程不等同于无限并发许可，仍需显式限额。

### 7. 在接收事务中决定会话，而非执行模型时

`received_at` 使用服务端首次接受事件的 UTC 时间，与消息去重、用户授权和会话分配一起落盘。同用户消息按持久接收序号排序。在短事务内读取最新空闲设置及当前会话：

```text
普通有效文字：
  无当前会话，或 received_at - last_user_message_at >= idle_timeout
      → 结束旧会话（若存在），创建新会话
  固定事件 conversation_id，并更新 last_user_message_at

/new：
  在接收顺序中的当前位置结束旧会话并创建新会话
  固定命令及后续消息归属，确认回复在按序执行时发送

/help、不支持内容：
  不延长有效用户消息计时；仅给本地提示，不触发模型
```

未授权、重复或接收失败的事件不刷新计时。模型成功/失败、回答耗时和轮询状态都不刷新该时间。历史仍只取当前事件之前、同用户/绑定/会话且确认投递成功的问答，沿用用户实际收到的回复而非为了缓存加入未送达或完整隐藏回答。

超时默认 30 分钟，范围 1–1440 整数分钟。更新后下一次接收事务读取新值；已分配事件的会话和已结束会话不重算。首次收到消息时惰性判定即可，无需清理定时器；界面展示空闲/预计截止不代表微信断线。跨重启保留时间；时钟回拨时不减少已持久化的最后时间，部署文档要求正常时间同步。

**替代方案：** 按模型完成时间会让慢调用人为延长会话；执行时临时选择当前会话会把排队消息串入 `/new` 之后的对话；定时删除历史会违背保留记录需求。

### 8. 中转站默认兼容，不虚构缓存能力

第一版实现 `compatible` 一种可用模式：发正常兼容请求，不发送未验证的 cache-control、缓存 Key 或特定厂商资源创建参数，不试探收费接口来自动识别供应商。模型服务可能已经自动前缀缓存，应用不能据接口自称兼容而保证支持。

`ContextBudget` 继续固定系统提示词在前、历史按原序、当前问题在后，保持相同部分内容稳定，不插入每次变化的时间或随机 ID。保留历史轮数和上下文预算裁剪；不为命中率保留无限历史，也不使用跨上下文的答案缓存。

`ModelRequestContext` 携带用户、binding 版本、conversation ID 和模型配置版本，仅作为内部归属；默认不为了“隔离”将这些随机 ID 注入 prompt 前缀。未来显式缓存句柄可按上述范围持久化，当前不创建伪句柄或宣称本地 Redis 能提供远端 KV 缓存。API 地址、Key、模型或系统提示词变化产生新配置版本；在途调用继续使用其快照，新开始的调用使用新版本并重新检查预算。

缓存 TTL 由供应商决定，本地会话 TTL 由管理员决定。前者失效时仍完整发送正确上下文；后者结束时即使供应商仍有缓存，也不发送旧私有历史。供应商复用相同公共系统前缀不等于跨用户泄露，应用授权仍完全独立。

**替代方案：** 写死一家供应商或给所有请求加同名缓存字段不能满足中转站兼容；只发最新问题会丢失上下文；均排除。专用缓存适配可另立后续 change，不把不支持当故障。

### 9. 用量独立于回答投递结果，未知不等于零

扩展模型调用边界，返回回答以及 `inputTokens? / outputTokens? / cachedInputTokens? / usageStatus` 等可空数据。只映射经过字段语义与测试确认的兼容响应用量，不假设任意名称相近的计数都可相加。优先确认当前 Spring AI 是否完整暴露这些字段；若丢失，使用受控的响应映射扩展，不打开全量 HTTP body 日志。

每次实际尝试有唯一 ID 和配置/用户/会话快照，网络调用前记尝试，返回后独立保存已知用量，再决定回复能否投递。回复为空/截断、用户被停用或发送失败时也尽可能记录已返回的用量；超时、连接中断或服务未返回 usage 时保持未知，不为补统计重发请求。重试遵循已有仅确定未发出/明确限流才允许的策略，每次尝试分别计数，再按唯一 ID 幂等聚合。

规范化计数使用可空整数，拒绝负数/溢出/同口径 cached > input 等不一致指标；计数异常不破坏有效回答。`cached_input_tokens` 是输入的子集，不再加到 input 上；无法确认是否同口径时未知。按用户、会话和时间范围汇总，并列出未返回用量的尝试数。命中率只对同时已知的 input/cached 数据计算并标明统计覆盖；没有可信价目与中转计费规则不展示节省金额。数据库写入失败不能为了补用量而再次调用模型。

**替代方案：** 用 UTF-8 估算冒充真实 token 或把缺失字段置零会误导用户；只统计成功送达的回复会漏掉已计费失败请求，均排除。

### 10. 管理认证与同源页面

首次空目录通过仅操作者提供的 `ADMIN_INIT_USERNAME` / `ADMIN_INIT_PASSWORD` 初始化一个管理员，密码用 Spring Security 的适当密码哈希保存；没有通用默认密码，缺少初始凭据时明确拒绝未初始化启动。初始化后移除初始环境变量；残留变量不会重置管理员。环境变量仅作容器引导秘密，文档提示限制部署文件和 Docker 管理权限，不把它们称为安全保险箱。

使用服务端会话、HttpOnly/SameSite cookie、CSRF 与请求来源校验；TLS 部署启用 Secure cookie，关闭不需要的跨域访问。登录失败限流、会话过期和退出失效；密码/Key 不写 localStorage、日志或 API 响应。中文页面对备注名、模型名、错误信息按文本转义渲染，不执行服务端或用户字符串。模型 Key 在设置 GET 中仅返回已设置标记，空白更新表示保留原值，替换必须显式输入，不能读回旧值。

主要 API 范围（最终 DTO 在实施时固化）：认证/退出；用户列表/新增/状态操作；用户下绑定任务创建、取消、状态、图片与配对提交；全局模型和超时设置；脱敏用量与审计。所有 binding attempt 访问同时校验 user 路径与任务所属，不存在聊天正文或任意文件读取端点。

服务可在模型未配置时启动管理端；模型请求入口返回受控未就绪状态，配置错误不使管理员无法修正配置。更新接口地址沿用 HTTPS 默认、受控本地 HTTP 例外与禁自动重定向的规则，不向意外目标发送 Key。

**替代方案：** 无密码内网页面、固定默认密码、公开扫码 API 均扩大开通权限；为简化直接开放数据目录又会泄露 token，均不采用。

### 11. 保持单容器与可回退的新部署

管理服务在容器 `8080` 监听，示例只发布 `${ADMIN_BIND_ADDRESS:-127.0.0.1}:${ADMIN_PORT:-8080}:8080`，操作者按文档选择指定 NAS 内网地址和受保护的 HTTPS/SSH/VPN 入口，不默认发布到所有接口。现有 `8081` 容器回环健康检查保留，管理健康不能因某一个用户等待扫码就整体失败。

新 Compose 默认数据源 `./data-multi-user`，显式 `user: "${ASSISTANT_UID:-0}:${ASSISTANT_GID:-0}"`，允许改回目录所有者 UID。镜像自身可继续非 root USER，Compose 覆盖满足本轮使用偏好，不要求扩大镜像其他运行场景权限。不挂 Docker socket、不 privileged、不自动递归 chown 宿主机目录。root 新建私有文件普通宿主机用户可能不可读，应在文档明确说明。管理员设置保存在私有数据中，模型基础引导配置不能在每次启动覆盖管理端已保存值。外部 application.yml 改为可选运维配置，不继续要求首次管理端部署先挂载含模型和 bot-id/owner-id 的旧配置文件。

用户已要求不配置 `stop_grace_period`：示例保持省略，因此必须把应用默认退出预算从原 20 秒调整到不超过 8 秒，为 Docker 默认约 10 秒停止等待预留空间；取消与状态保存优先，未完成外部操作保守标记。兼容自定义停止窗口时应校验/说明两者关系，不沿用 20 秒收尾却假装 10 秒足够。

继续 amd64/arm64 构建与镜像读写检查，补 Web 启动、root/non-root 权限与新布局拒绝旧目录的烟测。管理页的引入意味着 root 进程多了网络攻击面，建议只在受保护入口使用，并优先选择匹配目录所有者的非 root 身份。

**替代方案：** 无端口配置无法访问新增管理端；默认公网监听与 root 权限组合风险较大；直接覆盖旧数据难以回退，均排除。

## Risks / Trade-offs

- [扫码身份关系或多账号并存无法得到可靠证明] → 将协议验证放在实施前段；生产失败关闭，真实验收不打勾，不擅自改变绑定体验。
- [二维码被转交给错误的人] → 明确一次性邀请信任模型、短期限、管理员可取消和审计；不声称备注名验证了现实身份。
- [重绑、停用和迟到网络响应发生竞争] → 任务版本、授权 epoch、绑定版本、连接 generation 与激活事务的组合校验，并测试 ABA（停用后恢复）场景。
- [一库多用户的查询漏范围条件] → 复合约束、统一范围对象、恶意交叉 ID 测试；后台不暴露聊天正文降低接口面，但不能替代数据层约束。
- [一个中转站未提供 usage 或路由频繁变化] → 兼容请求与未知用量标识；不保证节省，不用付费探测或重试制造命中。
- [多用户小规模扩展仍有资源争用] → 有界并发、每用户及总积压、短事务；SQLite 与单实例能力不包装为无限扩展。
- [root 加管理端提高受攻击后影响] → 受限网络、认证/CSRF、私有目录、禁敏感挂载，记录非 root 替代路径；不承诺 root 能绕过所有 NAS 权限。
- [应用时钟变化影响空闲判断] → UTC 持久时间、禁止计时回退、文档要求主机正常同步；不以模型延迟代替活动时间。
- [当前旧 change 未归档而新设计替换其前提] → 本轮不改旧草案；后续同步/归档时先协调单用户与多用户约束，不能机械合并冲突要求。

## Migration Plan

1. 保留现有部署、镜像版本、配置及数据备份；本轮没有迁移任务，也不删除旧目录。
2. 在新的宿主机目录初始化多用户布局。启动前的布局探测遇到旧数据库/未知版本要无写入失败；无模型配置也能完成管理员配置。
3. 在受保护管理入口初始化管理员，保存模型设置，以两个授权微信账号完成真实身份与连接验证。现有旧容器若使用同一账号，应由操作者停止后再扫码，避免把重复登录副作用当成隔离错误。
4. 验证独立聊天、缓存用量未知/已知展示、30 分钟及自定义超时、停用/重绑、重启恢复和管理权限。自动化用可控时钟与合成接口，不为缓存演示自动发送额外付费请求。
5. 正式运行仅一个实例占用新目录。备份先停止实例并备份整个目录及受保护配置；恢复到匹配布局与版本，不仅复制运行中的单个 SQLite 主文件。
6. 回滚时停止新实例并重新使用原镜像和原独立目录，不用旧程序打开新数据库。重复扫码可能使旧 token 失效，回滚必要时仍需重新登录，不能保证远端凭据也随本地文件回滚。
