## Context

项目目前只有 OpenSpec，尚无 Java 工程或既有数据。产品动机与范围见 `proposal.md`；行为合同见四份新增规格。本设计涉及首次工程结构、两个外部协议、持久状态和凭据保护，符合需要设计文档的条件，不跳过 design。

运行环境为个人 NAS 上的一个 Docker 实例，首版目标固定为 `linux/amd64`（x86-64）与 `linux/arm64`，不包含 32 位平台。具体 NAS 型号、挂载目录及实际 API 地址/模型名由部署时提供，不阻塞业务实现；不要求敏感配置写入规划。微信协议参考此前查看的 [Python 项目](https://github.com/SiverKing/weixin-ClawBot-API) 及其链接的上游说明，视为互通参考而非稳定服务合同；实施验证时记录上游版本或 commit，并核实复用代码的许可。不会复制无明确许可的项目源码。

## Goals / Non-Goals

**Goals:**
- 一个 Maven 工程、一个可部署进程完成通道接入、对话编排及模型访问，保留足够清晰的职责边界。
- 正常路径简单，故障路径可诊断；将本地持久化保证与外部服务无法保证的 exactly-once 行为分开。
- 默认私有、低运维依赖，能够在无人值守容器启动和需要人工扫码之间平稳切换。

**Non-Goals:**
- 不建设通用插件系统、任意 JSON 协议映射器、分布式调度或多模块微服务。
- 不为未来工具调用预建工具表、执行器、沙箱或 Agent 循环；未来权限及确认机制另行设计。
- 不将当前未验证的协议字段、配额或生命周期写成不可调整的常量。

## Decisions

### 1. 单体分包，保留一个助手处理边界

选择 Java 21、Spring Boot、Spring AI、Maven；在实施验证时选定相互兼容的稳定版本并锁定 BOM 与依赖。按 `channel.wechat`、`conversation`、`assistant`、`model`、`persistence`、`runtime` 分包，不拆多个 Maven 模块。

```text
微信长轮询 ──→ 校验/身份过滤 ──→ 持久接收 + 游标事务
                                      │
                                单消费者按序处理
                                      │
                          指令处理 / 上下文选择
                                      │
                              AssistantService
                                      │
                       Spring AI ChatModel 适配
                                      │
                      自定义 Chat Completions API
                                      │
                            结果持久化 → 微信发送
```

通道层把消息转换为内部输入，持有微信 token、节点和关联令牌；对话层只处理身份、会话、轮次及业务文本。助手处理入口接受上下文、返回文本结果，未来可替换为模型与工具循环。模型协议 DTO 不传播到微信接入层；不再额外抽象一套通用模型框架。

备选方案是 Python 网关加 Java 后端，或从多 Agent 框架起步。前者增加运行进程和故障边界，后者没有当前业务收益，均不采用。

### 2. 微信协议独立适配，先验证而非完整照搬

用独立 Java HTTP 客户端实现二维码申请、状态轮询、配对验证、服务节点切换、`getupdates`、`getconfig`、输入状态及 `sendmessage`。启动/停止生命周期通知按上游可用行为做最佳努力，不能阻塞正常关闭。

首次二维码从已验证的官方入口申请；节点切换仅接受预期协议响应中的 HTTPS 微信服务节点，验证允许的主机范围，禁止携带凭据跟随任意跨主机 HTTP 重定向。公共登录请求与带 bot token 的已登录请求分别封装。消息发送逐层检查 HTTP、JSON、`ret/errcode`，日志只保留脱敏错误分类。

长轮询读超时要大于已验证的服务端轮询等待窗口，并支持服务端超时提示；与模型超时分开配置。输入状态为最佳努力辅助功能，失败不能使回答失败；在结束路径尝试关闭输入状态。

登录状态为：`WAITING_LOGIN → CONNECTING → CONNECTED`，临时故障进入 `RECONNECTING`，明确失效返回 `WAITING_LOGIN`。不照搬“24 小时强制重登”的客户端假设，不承诺固定 token 生命周期。重复失效只触发一次有效登录挑战，避免扫码材料被并发刷新。每次登录切换更新连接代次；旧代次的在途轮询响应不能覆盖新连接凭据或游标，发送前重新检查绑定和连接代次。

稳定消息标识、登录身份与 sender id 的关系、长文本上限、当前回复关联令牌有效性等，在第一阶段从实际返回值验证并记录。若目标账号根本不能使用该通道，则该接入阶段未通过；不得改接任意个人号 Hook 或自动转向另一个微信产品来宣称完成。

### 3. 无交互登录，身份授权独立于扫码

容器不依赖 stdin。选用受保护的本地文件作为最小登录运维入口，而非 Web 管理后台：
- 数据目录内 `login/` 保存当前二维码图片及含挑战标识、阶段、过期时间的状态文件，采用临时文件加原子替换。
- 需要配对码时，操作者按文档写入包含挑战标识和配对码的一次性提交文件；应用仅处理当前挑战并在消费后移除。
- 登录完成、挑战过期或账号切换时清理临时材料。拒绝过期输入、符号链接及超限文件，默认目录仅运行账号/操作者可读。

所有者通过本地配置中的机器人身份和消息发送者身份显式绑定；缺省拒绝。获取身份的操作说明允许操作者在受保护的本地诊断中查看候选身份并与自己的测试发送核对，配置仍需操作者明确提交，不自动信任首条消息。若无法人工可靠核对，不启用该绑定，必须先完成身份验证步骤。所有者未配置时可维持连接以完成诊断，但不保存未授权聊天正文或调用模型。

重新扫码得到同一机器人身份时恢复原绑定；得到不同身份时进入等待绑定，不复用原个人会话。暂不支持在线更换所有者；修改配置后重启生效。

### 4. SQLite 承担持久状态，不引入 MQ

选择 SQLite JDBC + 直接 JDBC/轻量映射，使用小连接池、短事务和单写入调度；不引入 ORM 方言适配或独立数据库服务。初始化启用外键、WAL、合理 busy timeout 和明确的持久写入策略，迁移使用版本化 SQL 与 schema 版本表，禁止自动破坏性重建。

建议最小数据模型：

| 数据 | 主要内容与约束 |
|---|---|
| channel_state | 机器人身份、节点、凭据、游标与连接版本；敏感字段不进入日志 |
| inbound_event | 机器人身份 + 稳定消息标识唯一；接收序号、发送者、文本/类型、关联令牌、处理状态 |
| conversation | 绑定身份、会话标识、创建时间和当前会话状态；每个绑定最多一个当前会话 |
| turn | 关联事件、业务会话、用户输入、完整模型结果、实际待发/已发文本、发送标识和结果状态 |
| schema_version | 已应用的持久化结构版本 |

未授权事件只保留推进游标/去重所需最小元数据，不保存正文；异常消息隔离只记录必要诊断信息。入站稳定标识未确认前不能用文本哈希顶替，否则会吞掉用户有意重复的问题。

拉取成功后，在同一短事务中保存可处理事件、明确忽略/隔离的结果和新游标；事务失败不推进游标。只有事务提交后，消费者才看见新工作。外部网络调用不持有数据库事务。数据库不可写时停止消费和继续拉取，不能假装消息已接收。

持久队列替代纯内存队列，避免进程退出造成“游标已推进、消息却丢失”。对未处理事件数和磁盘剩余空间设置可配置阈值，达到阈值暂停新增轮询并显示积压原因；不承诺无限积压能力或无限上游保留时间。

NAS 本地磁盘目录 bind mount 到 `/app/data`；不支持把活动数据库置于 SMB/NFS。启动时持有数据目录独占进程锁，第二实例拒绝启动，不把 SQLite 的写锁误认为完整的应用单实例保护。

### 5. 单消费者保证消息和 `/new` 的相对顺序

一个独立接收循环和一个对话消费者足够服务个人用户，不为模型调用阻塞长轮询。消费者按持久接收序号执行；消息开始执行时再决定当前会话，而非接收时提前绑定。

`/new` 的新会话创建、旧会话切换和事件完成状态在同一事务中提交，使重复入站不会创建多次新会话。该指令的确认消息即使投递失败，也不能回滚已完成的会话切换；诊断需准确报告。`/help`、未知指令和不支持媒体的能力提示同样排队，但不进入模型历史。

不主动合并连续输入，不默认取消正在生成的回答；这些会改变用户可观察行为，未来有需要再增加。

### 6. 明确外部副作用与崩溃窗口

将事件生命周期划分为可恢复阶段，发送前持久记录发送标识及状态，不承诺两个远端系统和本地数据库之间有分布式事务：

```text
RECEIVED → PROCESSING → RESPONSE_READY → SENDING → SENT
                 │                         │
                 ├─ FAILED                 ├─ SEND_FAILED
                 └─ INTERRUPTED            └─ DELIVERY_UNKNOWN
```

- `RECEIVED`：仅持久接收，重启可自动继续。
- `PROCESSING`：调用前已记录；重启后保守标记 `INTERRUPTED`，不自动再调用模型，即使崩溃可能发生在实际发出请求之前。
- `RESPONSE_READY`：完整结果与待发送文本已保存，尚未开始发送；重启可以在账号和关联令牌仍可用时尝试发送，不重新生成回答。
- `SENDING`：发送前已持久标记；未保存明确结果就重启或读超时，转 `DELIVERY_UNKNOWN`，不自动重发。
- 明确失败保存错误类别；只有未发出请求或服务明确允许重试的情况按受控策略再试。

上述状态图是工作阶段的简图；实现中将轮次类型、模型结果状态和回复投递状态分别保存。只有普通对话、模型成功且回复确认送达三个条件同时成立时，才进入后续模型上下文；错误提示或指令确认的发送成功不等于模型轮次成功。

成功回答先保存模型结果、格式化文本和发送标识，收到业务成功后再标记 `SENT`。错误提示、帮助、新会话确认也需要复用同类发送状态保护，而非绕开防重边界。已知被服务拒绝的发送重试采用上游验证过的发送标识规则；语义不明确时不重试。

不确定/失败轮次在本地状态和诊断中可见，不重用另一条消息的关联令牌强行补发。用户可以重新发起问题；自动重试只对已明确安全的条件开放。此策略宁可留下可解释的中断，也不默默重复消耗额度或刷屏。

### 7. 历史完整保存，上下文按成功轮次裁剪

采用应用自己维护的持久历史作为唯一真相，不叠加 Spring AI 隐式内存记忆造成双份上下文。上下文始终是系统提示词、当前会话最近完整成功轮次、当前用户输入。只有回复业务确认成功的轮次进入后续历史选择；对已截断回答使用实际已发送文本，完整原始生成结果只作持久记录。

设置可配置的近期轮数、上下文容量、输出预留和安全余量。容量由操作者根据真实模型填写，不能从未知模型名猜测。可识别模型使用匹配的 token 估算；未知模型使用带消息封装余量的保守 UTF-8 长度估算，并注明无法保证与任意服务端 tokenizer 精确一致。发生服务端上下文拒绝时不给出虚假的“预算保证”，而是诊断并指导调整。

最旧完整轮次优先移出输入，不破坏 user/assistant 配对。系统提示词和当前输入仍超预算时提示用户缩短，不静默截断本次问题。不做摘要、嵌入、长期记忆或历史自动清理。

### 8. 固定兼容协议，端点组合只有一种规则

用 Spring AI 的兼容 ChatModel 接入；把基础地址与固定 completion path 显式配置，禁用隐式提供商默认值、自动记忆及默认不可控重试。适配配置规则如下：

| 配置项 | 第一版约定 |
|---|---|
| api-base-url | 服务 origin 加可选网关前缀，末尾不含 `/v1` 或完整接口路径；去掉末尾斜杠后只追加一次 `/v1/chat/completions` |
| api-key | 必填，从环境或受保护的只读配置读取；不写入数据库和普通日志 |
| model | 必填，按原值传递，不自动改成其他厂商模型 |
| system-prompt | 配置默认助手行为，不提供远程修改配置指令 |
| context-capacity / output-budget / history-rounds | 显式验证有效范围，输出预留与余量必须小于容量 |
| request-timeout / total-time-budget / max-retries | 互相一致并有上限；默认保守，文档列出实际实现默认值 |

只接受明确的 HTTP/HTTPS 地址，拒绝 URL 用户信息、查询和片段；远程服务默认要求 HTTPS，可信 NAS 内网 HTTP 如确有需要须显式启用并说明密钥明文传输风险。模型请求不跟随将 Authorization 泄露到其他主机的重定向。

请求只携带 `model`、`messages`、`stream=false` 及经过实际服务验证的输出长度控制参数。第一版不默认发送 temperature、工具、JSON schema 或其他厂商参数。输出预算映射在兼容性验证中确定；如实际服务要求不同的标准长度参数，只在模型适配配置中处理，不扩展成任意请求映射器。

提取有效文本，检查候选、空值、finish reason 和截断情况。不执行模型返回的工具调用。对模型输出长度终止增加提示；对微信发送上限再次进行按 Unicode 边界的长度检查，第一版标记截断而不是多消息分片，减少部分投递和重试状态组合。完整原文与实际发出文本分开保存。

模型重试限定到可判定尚未发出的连接错误，以及明确拒绝本次处理的限流/暂时不可用响应。通用 5xx 不自动等同于“从未执行”，读超时也不重试；超出总时间预算结束本轮。配置里没有第二提供商作为隐式 fallback。

### 9. 容器状态、凭据与运维

提供同一套多阶段 Dockerfile、单服务 Compose 与 Docker Buildx 构建说明，目标为 `linux/amd64` 和 `linux/arm64`。构建阶段可在构建机原生架构生成通用 Java JAR，运行阶段按目标平台选择支持两种架构的 Java 21 Linux 基础镜像并以非 root 运行。SQLite JDBC 原生库须在各目标架构/基础镜像组合中验证，不能用 amd64 测试结果代替 arm64。分别记录构建支持、镜像构建结果与 Java/SQLite 运行测试结果；仿真测试须注明仿真环境，未执行的项目标为未验证。按操作者确认，构建/发布由 GitHub Actions 执行，镜像仓库使用 GHCR。PR 和普通开发分支只执行验证；默认分支和版本标签在两架构验证通过后可发布，多架构正式标签不得包含未通过检查的架构。构建任务无 packages 写权限，发布任务使用仓库的短期 GITHUB_TOKEN，不引入微信凭据或模型 API Key；第三方 Actions 固定到具体提交。

工作流分别加载每个目标架构镜像，以非 root、无网络、临时持久卷运行 Java/SQLite 冒烟检查，并在重建容器后检查合成会话/历史。arm64 在 x86 runner 上通过 QEMU 执行时明确记录为仿真，不冒称 NAS 原生实测。只发布已测试的镜像制品，保留构建/基础镜像摘要、架构、合成检查结果和测试报告。工作流文件通过本地校验不等于 GitHub CI 已运行；首次实际 CI 结果须由操作者提交仓库触发后补充。

本机 Docker 是否运行不阻塞工作流与业务开发。操作者负责 NAS 部署、权限/备份演练、真实出网和最终微信到模型验收；代理交付说明和检查清单，并保持待 CI/待操作者验收状态，不声称构建脚本存在就代表真实 NAS 已可用。

数据目录建议由应用 UID/GID 持有，目录权限 0700、敏感文件 0600；如 NAS ACL 语义不同，文档要求达到等价限制。配置目录只读挂载，密钥文件权限收紧；不要求把普通 NAS 用户加入无限制 Docker 权限组。凭据目前依赖文件权限及 NAS 磁盘/备份保护，并非应用层加密，文档明确这一边界。

只开放容器内部 loopback 健康端点，可使用 Spring Boot Actuator 的存活/就绪组；Compose 不映射业务或管理端口。不探测模型来定期产生付费请求。状态同时输出连接状态、绑定状态、最近模型调用结果、积压和不确定轮次数；模型 readiness 根据配置及最近实际调用判断，不声称未调用过的模型已互通成功。

Docker healthcheck 只检查本地进程/核心循环存活；`restart: unless-stopped` 针对进程退出，并不会自动因 unhealthy 重启。外部看门狗也不得把等待扫码当重启条件。数据库不可用等本地致命问题按失败处理；微信失效和模型短期故障保持进程存活供操作。

关闭先停止新轮询和消费者领取，再等待正在执行工作到宽限期；超时取消并保留前置状态，由启动恢复规则处理。生命周期通知用独立短超时，不延长关闭期限。日志默认只输出关联标识、错误类别、耗时与计数，不记录聊天正文、完整用户标识、鉴权头、二维码、token、配对码及原始错误 body。

### 10. 先做真实互通门槛，再完成完整功能

实施顺序为最小工程和模拟契约测试 → 真实微信收发与实际自定义模型两轮对话验证 → 完整持久对话、授权与恢复实现 → amd64/arm64 容器构建及运行验证 → 实际 NAS 部署验收。按操作者要求，具体 NAS 型号、实机架构与挂载条件不再作为业务开发前置门槛；任务 2.6 后移到第 7 节容器化阶段，保持未完成直到真实执行其验证。真实微信/模型验证仍需要操作者扫码、提供本地配置并确认费用，不以 mock 代替；NAS 相关检查是后移而非默认为通过。

测试分为纯单元测试、模拟两个外部协议的契约测试、临时磁盘上的持久化/故障注入测试、容器生命周期测试及人工真实互通验收。无凭据环境可以运行前四类；第五类单独报告通过、失败或未执行。

## Risks / Trade-offs

- [微信服务接口、账号资格或协议版本变化] → 接入门槛提前验证；保留契约样本和参考 commit；缺失前提明确停止该集成，不虚报完成。
- [收发和模型执行没有跨系统事务] → 持久阶段、稳定入站标识和不确定状态；拒绝承诺 exactly-once，宁可人工重试也不盲目重放。
- [配置的兼容 API 并不支持全部标准字段] → 最小字段集和真实契约验证，不依赖框架默认参数；未支持的协议差异限于模型适配层。
- [未知 tokenizer 导致估算偏差] → 明确容量配置、保守估算和余量，保留错误诊断，不把启发式估算宣传为硬性 token 保证。
- [NAS 文件权限、网络盘或 SQLite 原生库不兼容] → 本机数据盘、启动自检、目标架构容器测试、操作说明；不无条件保证任意 NAS。
- [本地磁盘和备份包含聊天隐私及凭据] → 最小权限、日志脱敏、备份访问控制；磁盘加密依赖部署环境，不假装本方案已提供应用层密文存储。
- [无 Web 管理页导致首次扫码操作略繁琐] → 使用少量受限文件和完整操作步骤；验证用户实际可完成，再考虑独立管理页变更。
- [完整历史和待处理事件持续增长] → 监控磁盘和积压阈值，暂停接收而非静默丢弃；历史清理策略不在首版自动执行。

## Migration Plan

1. 没有既有业务数据需要迁移。先完成微信/模型协议兼容性验证并记录可用版本与账号条件；容器化阶段分别记录 amd64/arm64 构建和运行结果，实际 NAS 架构在部署时与对应镜像核对。
2. 创建受保护的 NAS 本地目录和只读配置文件，确认 UID/GID、容量和出网；使用目标架构镜像启动单实例，初始化带版本的数据库。
3. 完成扫码及必要配对，人工确认所有者绑定；验证普通文字、两轮上下文、`/new`、重启恢复和断网恢复。
4. 备份优先采用停止应用后复制完整所需数据目录的方式，排除短期二维码/配对材料；只读配置与密钥独立安全备份。若提供在线备份，必须使用 SQLite 支持的一致性机制，不能只复制活动数据库主文件。
5. 升级前停止旧实例并取得一致性备份，再使用新镜像执行版本化迁移；不允许两个版本同时连接同一目录。若启动/迁移失败，保留故障数据副本，用旧镜像和兼容备份恢复，不尝试让旧版本强读新结构。
6. 恢复后核验当前会话与未完成状态；凭据若已失效则重新扫码。灾难恢复到旧备份可能落后于远端已执行操作，应先人工核对未完成轮次，不自动重放潜在重复任务。

## Open Questions

以下仅是部署输入，不改变本变更范围或架构：
- 目标架构已定为 amd64/arm64；部署时核对实际 NAS 属于哪一种及其可用内存、目录路径和运行 UID/GID，不在继续业务开发前索取具体型号。
- 实际 API 基础地址、模型名、可用上下文容量、输出参数支持和超时偏好；密钥只在本地部署配置提供。
- 实际微信账号的绑定过程和发送限制的测量结果；由前置验证任务记录，无法满足规格时不得将该阶段标为完成。
