## Context

动机与范围见 [proposal.md](proposal.md)。本设计基于当前已实现的多用户运行链路，不把原 change 未完成的真实验收视为已通过。

以下代码现状描述为提案创建时基线。2026-09-30 操作者确认后续实现及测试直接通过配置连接已有外部 MySQL/Redis，不单独拉取或部署数据库/缓存镜像。已授权配置的项目专用库建表、合成数据及项目专属缓存前缀读写；这不包含停止、重启、清空共享服务或恢复覆盖数据。先前实施记录中的镜像拉取失败是历史事实，不再是继续接线与安全测试的前置阻碍。

- `ManagedStore` 目前持有一个 SQLite 连接，`transaction` 全局同步；启动恢复会更新全部处理中事件，因此不能只替换 JDBC URL 后运行多个实例。
- `ManagedConversations.history` 查询同范围的全部成功送达问答，`ContextBudget` 才裁剪历史轮数和容量；当前没有匹配该历史访问模式的专用组合索引。
- `ManagedTurnWorker` 负责持久阶段，`ManagedModelPool` 按模型配置版本复用客户端。`finishSend` 是确认投递边界；只有 `SENT` 且 `model_succeeded=1` 的回复才属于后续上下文。
- `ContextBudget` 目前只拼接固定 system、历史和 user；服务已有可注入 UTC `Clock`，但没有动态时间输入。旧缓存规格要求固定前缀稳定，不等于禁止在请求尾部提供运行时信息。
- 旧单用户运行与 SQLite 存储、6 个主代码探针、部分 CI 契约仍存在。共享 `PrivateStateFiles`、微信协议客户端、模型适配、健康检查不能随旧包整块删除。
- 操作者有现成 MySQL/Redis，明确接受全新安装、丢弃旧账号与历史，不要求数据迁移。具体版本、连接端点和权限尚未核实；不在提案中猜测版本、要求升级或索取秘密。

## Goals / Non-Goals

**Goals:**

- 单一 MySQL 业务真源与可丢弃 Redis 热历史；热点命中消除历史正文查询，但仍做轻量数据库授权/版本检查。
- 保留既有管理认证、扫码身份、范围隔离、接收时会话分配、真实用量和未知投递保护，以真实数据库与缓存故障测试覆盖替换边界。
- 将时钟依赖、缓存边界与 SQL 事务显式化，同时控制新增抽象数量。

**Non-Goals:**

- 不做 SQLite 导入、跨库双写、旧 SQLite 原地升级、旧文件清理或两套生产存储可选模式。仅支持下述明确识别的本项目 MySQL V1 → V2 追加式布局升级，不通用接管未知布局。
- 不做多实例服务、自动主备接管、Redis 消息队列、聊天答案缓存、模型厂商显式 KV 缓存或聊天正文管理页面。
- 不承诺模型回复严格逐字遵循时间信息、不承诺总延迟倍数、不把系统时间来源解释为联网获取新闻或实时事件能力。

## Decisions

### 1. 保留 repository 职责，替换 JDBC 事务实现

采用 Spring 管理的 MySQL 数据源/有界连接池和 Redis 客户端；保留当前按用户、设置、会话、用量、审计划分的 repository，替换连接生命周期与 SQL，不为已决定退出的 SQLite 建立双后端适配层，也不同时引入 ORM 重写。

初始化和未来 schema 演进采用版本化 MySQL 脚本与明确版本标记；在运行面启动前检查专用 schema。空 schema 才能初始化，匹配版本可打开，未知/部分初始化/更新版本必须失败关闭，不能 `DROP` 后重建。不要把 MySQL DDL 当作 SQLite 的整套事务回滚，初始化中断需记录可诊断状态；重试只执行明确可重入步骤，不启动半成品布局。

**已确认的 V002 补充：** 本 change 实施期间已在授权库执行 V001，其 `conversation` 缺少原管理接口需要的数字分页游标。V001 内容及摘要保持不变；V002 用单条追加式 `ALTER TABLE conversation` 增加 `sequence BIGINT NOT NULL AUTO_INCREMENT`、序号唯一索引及 `(user_id, sequence)` 分页索引，保留 UUID 主键、全部旧字段/行和外键。已有 V1 行由数据库首次分配稳定唯一序号，不把这一分配宣称为旧 SQLite 插入顺序；之后新行使用数据库自增值，重开不重新编号。管理员元数据仍按用户范围、`sequence < before`、倒序 `LIMIT` 分页，不变更 API 字段或改为 OFFSET。

只读预检接受完整 READY 且原脚本/结构摘要精确匹配的 V1 或当前 V2；其他版本、部分初始化或篡改布局直接拒绝。取得独占锁并再次验证后，V1 升级先持久写入 `version=2,state=INITIALIZING`、版本链脚本摘要并清除旧结构摘要，再执行 V002。完成后保存新结构摘要并置 READY，最后才推进运行 epoch 和恢复/启动业务；安装 ID 不变。DDL 失败或进程中断保留 INITIALIZING，下次启动拒绝自动猜测修复，不能盲目重跑 ALTER、降回 V1 或清表。空库先执行不变的 V001，再走同一 V002 升级路径；V2 重开不执行升级。第二实例在升级写入之前被锁拒绝。

新增测试分别记录已授权现有 V1 → V2 与 V2 重开、真实引擎合成分页/数据保留、无网络升级中断分类。不会为重跑升级而把 NAS 降回 V1，也不在共享库制造损坏布局；这些实际破坏性故障场景仍由 2.3 保留待验。配置测试入口单独显式允许已识别布局升级，普通单元测试不连接外部服务。

使用明确长度的标识列、适配 Unicode 的正文列、64 位序号/时间/用量，标识比较固定精确语义。把 SQLite `last_insert_rowid`、`ON CONFLICT`、`PRAGMA` 和错误码分类替换为验证过的 MySQL 行为。活动绑定、活动邀请、当前会话的条件唯一性使用独立活动关系表与唯一键表达，历史表保持不可混淆的归属；不通过普通索引或仅靠 Java 判断替代数据库唯一性。

事务采用明确隔离级别与必要行锁：用户/绑定变更和接收时锁定对应用户范围；全局积压限额需要短暂锁定统一容量状态，并按固定次序领取用户/会话锁。每个转换校验原状态和受影响行数，使用唯一键作最终去重保障。不能只移除 `synchronized`；同用户工作顺序仍由公平调度器维持，数据库领取也须条件更新防重入。纯数据库事务可在明确安全的边界有限重试死锁，但绝不重试包含已发出模型或发送操作的整个业务阶段。

**替代方案：** 只换驱动保留单连接无法消除应用锁竞争；所有逻辑转为 ORM 或同时兼容 SQLite 会扩大改造和测试面，因此均不采用。

### 2. 同一 schema 只允许一个活动实例

采用专用、不可归还连接池的 MySQL 会话持有运行命名锁；锁名由应用名和目标 schema 的稳定摘要确定。获取顺序为配置/只读布局检查、实例锁、布局初始化或校验、运行 epoch 更新、孤立工作恢复、启动连接运行面。锁由数据库管理，不用本地文件锁保护远端 schema，也不用可被缓存淘汰的 Redis 锁作为运行所有权。

MySQL 中保存每次运行的 epoch；每个业务事务和外部操作发起前都核对实例有效性及原用户授权。锁连接故障触发不可逆的本进程停止接收/调度，取消在途工作，不能通过连接池透明重连恢复旧 epoch。第二实例必须在任何恢复写入前被拒绝。所有权验证、连接丢失与迟到结果在真实 MySQL 故障测试中验证；不声称数据库锁能原子撤回已经发到外部服务的请求。

恢复只处理此前运行遗留状态；已发出但不确定的操作标记中断/未知而非重试。迟到已知用量仅按不可变原 attempt 归属幂等记录，不能推动新生成或发送。MySQL 不可用期间不把 Redis 当授权或账本，无法写回的结果保持未确认并在恢复时保守分类。

命名锁 API、驱动自动重连设置、连接超时与选定隔离级别须在实施第一步对实际版本核验；这里没有多实例故障转移承诺。

**替代方案：** 只在文档写“启动一份”无法阻止误操作；分布式调度/租约接管不属于本轮，用 Redis 锁不能消除数据库全局恢复的风险。

### 3. 从数据源限制历史，并建立可靠版本标记

为 `inbound_event` 增加以 `(user_id, binding_id, conversation_id, sequence)` 为核心的历史访问索引，保留 `turn.event_sequence` 与待处理状态索引。查询先约束完整范围、`sequence < 当前事件`、`CHAT`、`SENT`、模型成功，再 `ORDER BY sequence DESC LIMIT N`；应用仅把这 N 对反转为正序，之后才按 token/字节预算继续裁剪。用实际执行计划检查 JOIN、排序和过滤成本，索引优化不能只以名称存在为证据。N 为 0 时跳过历史正文查询与 Redis。

会话增加 `history_revision`、`confirmed_turn_count`、`last_confirmed_sequence`：只在成功模型问答第一次由发送中转为确认送达时，在同一数据库事务内推进。序号不是连续整数，不能用 `sequence + 1` 推断历史是否完整。重复完成、失败发送、未知投递及本地命令不推进历史版本。

新增轻量历史读取上下文，返回授权后确定的 user/binding/conversation、当前事件边界、历史 revision/计数/水位及配置快照。历史元数据和回源正文在一致的短事务快照下读取；Redis 网络操作必须在事务结束之后。模型实际发起前继续使用现有 observer 校验授权，缓存不能替代这一步。

**替代方案：** 全历史查询后裁剪转移不了数据库和内存成本；按最新任意 N 条取出再过滤会漏掉可用问答，因此只对合格完整轮次做 LIMIT。

### 4. Redis 保存带版本的完整窗口，不缓存提示词

增加一个窄职责的历史访问服务和可关闭的缓存组件，不改变模型客户端职责。键结构设计为 `talkweave:<installation-id>:<run-cache-epoch>:history:v1:<user>:<binding>:<conversation>:<model-config-version>`；所有部分由服务端已授权对象生成，绝不接受客户端传入的完整键或缓存指针。

`installation-id` 持久属于该 MySQL 安装，`run-cache-epoch` 每次应用启动重新随机生成，不复用 Redis 中旧运行的窗口。这牺牲重启热命中，但用最小机制解决数据库恢复后旧/新正文串入的问题，旧键按有限 TTL 自然退出，无需扫描或清空共享实例。

缓存值包含格式版本、完整范围、模型配置版本、历史 revision、合格轮次总数、末尾确认序号、窗口容量、是否覆盖全部历史以及有序的 `(eventSequence, userText, deliveredReply)`。只缓存未加时间/系统提示的原始可用问答。配置版本进入键，热更新后新调用按新预算冷启动；旧在途回填不能覆盖新配置窗口。

有效命中条件：范围和格式一致；缓存 revision/计数/水位等于数据库读取快照；所有轮次早于当前事件且顺序合法；缓存能够提供所需 `min(N, eligibleCount)` 个完整问答。通用接口遇到已确认水位不早于当前事件时，不推断尾窗可用，直接做带截止序号的 MySQL 查询，并且不把该历史切片回填为最新完整尾窗。正常按用户顺序执行满足水位早于当前消息。

缓存轮数取当前模型配置 N；单窗口上限初始建议 256 KiB，TTL 初始建议 60 分钟，均为可校验服务配置而非性能承诺。超字节限制不写入不完整窗口，当次仍使用有界 MySQL 结果并继续做模型预算裁剪。TTL 和会话空闲超时各自独立；仅成功校验、写入完整窗口时更新缓存期限，不为 Redis 命中刷新数据库活动时间。

**替代方案：** 只按用户缓存会跨重绑/新会话污染；只靠 TTL 无法发现提交后缓存丢更新；缓存完整 Prompt 会冻结日期并绑定旧模型配置，均不采用。

### 5. 回填和送达后更新都有版本约束

读取过程：短事务生成授权/版本快照，结束事务后尝试 Redis；有效命中直接得到历史窗口，未命中以新的短事务重新确认授权并读取有界正文，再在事务外回填。新一轮窗口仅作为当前模型调用前的历史输入，时间和当前问题在后续组装。

回填采用单键原子比较写入：旧 revision 不能覆盖缓存中较新 revision；同 revision 不以较小覆盖范围替换更完整窗口。版本在比较逻辑中必须精确处理 64 位值，不能经不安全的浮点转换排序。即使缓存键被驱逐后迟到旧值重新写入，下次读也必须与 MySQL revision 比较后拒绝它；原子写入本身不被当作授权依据。

确认发送事务返回一次性不可变的提交结果 `(scope, oldRevision, newRevision, sequence, pair)`。事务提交后才维护 Redis，更新只接受匹配前一 revision 且完整的窗口，幂等追加并裁剪；重复/较旧版本无操作，出现间隙不跳级追加。若该轮已有经校验的前置窗口且可证明其与 `oldRevision` 一致，可构建新窗口后比较写入；否则留待下一轮回源，不在每个失败更新后立即追加一次全库读取。

版本推进不依赖 Redis 成功，Redis 失败不能抛回发送阶段造成回滚或重发。该方案无需跨 MySQL/Redis 分布式事务，也不新增消息队列或可靠缓存 outbox：缓存允许丢失，数据库 revision 保证读时发现陈旧状态。缓存版本不符时拒绝该窗口并回源；数据库授权、运行所有权或可靠读取无法确认时才停止业务，不能把未知缓存当空历史静默继续。

**替代方案：** 每轮删除窗口会使连续聊天持续冷启动；单纯追加会受重复回调和丢更新影响；全套 CDC/outbox 对可丢弃缓存成本过高。

### 6. Redis 有界降级，MySQL 故障停止业务

初始建议单次 Redis 命令/连接等待预算 100 ms、每阶段缓存总预算 250 ms，包含连接获取、重试和回填；它们是待 NAS 验证的可调默认值，不是外部服务 SLA。采用有界客户端队列和有限并发，故障连续发生后暂时旁路缓存并有限探测恢复，不额外重试模型。不要在未使用的后台 executor 中积压大量缓存写入。

数据库回源受现有调度并发和连接池限制；同键并发重建做进程内有限合并，保持用户间公平。损坏或超限值视为未命中，解析前检查字节上限。缓存命中保留轻量 MySQL 授权读取，这是安全与性能之间明确的折中。

活性不因单独 Redis 故障失败；管理诊断新增脱敏 `historyCache` 状态和低基数计数，内部健康保持现有访问边界。指标区分 hit/miss/stale/error/bypass、正文查询量、历史阶段耗时；不记录聊天正文或把 user/conversation 作为指标标签。MySQL 丢连接、无法可靠记账或实例锁失效时，业务就绪失败并停止新操作。

**替代方案：** Redis 故障让全应用退出会把优化依赖变成可靠性单点；在 MySQL 故障时靠缓存继续对话无法保持授权和账本，均不采用。

### 7. 时间上下文作为请求尾部的独立受信任消息

增加可注入 `Clock` 和配置 `ZoneId` 的时间上下文构造器，由 `ManagedTurnWorker` 在历史准备结束后生成一次时间快照，传给 `ContextBudget`。默认 `managed.conversation.time-zone=Asia/Shanghai`，启动验证，修改后重启生效；不为本轮增加管理页时区设置或用户地理位置推断。

消息顺序为固定 system、原顺序历史、动态 system 时间上下文、当前 user。时间消息只由服务端构造，包括当前本地日期/时分秒/星期/时区/偏移和有明确标签的消息接收时刻；说明前者是生成时参照，后者是理解排队消息相对时间的参照。原问题独立，不把拼接在用户文本中的伪指令当系统信息。

预算器把这条消息算入最低成本后再裁剪完整历史；不足时使用现有本地超限回复，不发起付费调用。CompatibleChatClient 的重试复用同一列表，下一轮重新采样；不把时间落入历史缓存或改写数据库原文。使用常规消息字段，测试当前兼容网关对历史后 system 消息的支持；不以隐藏丢弃时间/角色或新增专用参数规避不兼容。

此排列保留静态 system 和原始历史内容，但因为上一轮的动态尾部不进入持久历史，不能承诺后一轮包含前一请求的全部字节前缀。原 `model-cache-accounting` 的真实性能/用量原则继续保留，相关测试从“整个前一次请求是完整前缀”调整为“静态 system 与相同原始历史不变”。

**替代方案：** 启动时写日期会过期；每轮修改首条 system 会过早改变公共前缀；仅设置容器 TZ 不会把时间传给模型。

### 8. 清理矩阵与独立诊断产物

MySQL 路径和行为测试接管后，删除 `AssistantRuntime`、两个旧 runtime configuration、旧 `ConversationWorker`、`ConversationRepository`、`SqliteStore`、旧 `LoginCoordinator`/`IdentityVerifier`/`InboxReceiver`/`WechatOutbound` 及其专属配置与 SQL。当前 SQLite 版 `ManagedStore` 也被替换，生产包移除 sqlite-jdbc 和 SQLite 专用启动参数；不保留可激活旧链路的 profile。

将共享模型配置从 `AssistantProperties.Model` 的旧单用户外壳中提取，保留现有管理配置序列化语义和校验；保留 `PrivateStateFiles` 的权限/符号链接防护、`WechatApiClient`、`ScannerIdentityResolver`、`ContextBudget`、回复格式化、模型池及健康检查。删除无调用的 `ManagedTurnWorker.compatibleModel()`；其他无调用候选须重新搜索调用方再删。

真实联调与容器探针移为显式构建的独立诊断产物；不为此强制拆分整个项目为多模块。`PrivateProbeFiles` 与探针一起移动，先解除双账号探针对旧单账号工具辅助方法的耦合。SQLite 专属 `ContainerStorageProbe` 退出，新 MySQL/Redis 容器验证通过正式应用接口与专用诊断 classpath 执行；正常 `HealthCheck` 仍随运行包发布。测试夹具继续只在 test classpath。

删除与替代逐项记录到覆盖映射：旧 SQLite 迁移/单用户文件授权测试可退役；状态恢复、权限、防串用户和未知投递等场景迁到 MySQL；Redis 和时间测试新增。Node 页面竞态、管理安全、模型协议与用量测试继续保留，不以测试数量下降作为收益目标。

**替代方案：** 整包删除 `runtime` 或 `persistence` 会带走共享安全代码；只删除测试而保留退役生产路径不能精简真实维护面。

### 9. 部署和验证使用外部服务，生产与测试权限分开

正式 Compose 仍仅包含应用服务，通过环境变量或受保护配置文件连接现成 MySQL/Redis；保留回环 8680、内部健康端口、只读根文件系统、受限权限和材料目录。示例列出 MySQL URL/schema/user/password、Redis endpoint/user/password/TLS、缓存配置和时区，不写真实值。准备 schema 的建表权限与日常运行最小权限说明分开；应用只初始化空的已指定 schema，不创建/删除 NAS 的数据库或用户。

将本地目录语义明确为私有材料，不再作为“备份业务数据库”的依据；数据库不可用诊断和 MySQL 备份由数据库检查替代本地 SQLite 文件检查，材料目录低磁盘检查仍只用于材料安全。历史 Redis ACL 限于项目键前缀与必要命令；不调用 `FLUSHALL`、`FLUSHDB`、`CONFIG SET` 或遍历其他项目键，TLS 校验失败不自动降级。

测试通过显式连接配置使用已有外部真实 MySQL/Redis，记录并核对实际服务与客户端版本，不拉取或启动独立 MySQL/Redis 镜像，也不要求另建服务实例。隔离以操作者已授权的项目专用 schema、每次测试的合成数据范围和 Redis 随机子前缀实现；不得把已承载真实业务的库自动当成可重置夹具。单元测试不要求网络；集成测试须显式启用并指定连接配置和目标范围，默认不读取本地 NAS 凭据或生产配置，未配置时不自动连接。真实 SQL、锁与原子脚本仍须在实际引擎验证，不能用 SQLite/H2 或假实现替代证据。

故障注入优先在应用侧中止测试自有连接、通过本机代理模拟断连/延迟/超时，或控制本次合成调用的回调顺序；不停止、重启共享 MySQL/Redis，不改全局配置、终止其他连接或清库。合成数据优先事务回滚，需提交才能验证的状态仅限已授权的测试范围；不以清表恢复初始状态，缓存使用有限 TTL。涉及恢复覆盖、部分 DDL、未知布局等无法在现有资源上安全执行的场景保留待验，不把局部模拟标为真实恢复通过，也不因此阻断其余可安全推进的实现。

构建阶段编译/单测，外部集成阶段通过显式配置和受限凭据连接授权资源；应用镜像烟测只放行配置的外部数据库/缓存和合成微信/模型端点，不访问真实微信或付费模型。CI 不继承操作者本地 NAS 配置，运行外部集成需独立显式提供已授权配置，缺少配置不算验收通过。amd64/arm64 仍分别验证正式应用镜像，不新增数据库镜像要求；发布继续依赖全部所需检查，不从另一份未验收镜像重新构建发布。

性能验证固定数据集与假模型延迟，比较优化后的 MySQL 直读、Redis 冷/热缓存、Redis 故障四种路径，使用相同 N、容量和并发，包含单会话 100/1000/10000 轮及并发 1/4 的合成负载；记录 p50/p95、正文与元数据查询量、命中率、连接池等待和模型/整轮耗时。硬性正确性门槛是有效命中不加载历史正文、回源有界、并发/故障不破坏语义；加速幅度按实测记录，热缓存不改善时需报告原因和调参结果，不伪造阈值通过。

**替代方案：** 强制拉取数据库镜像不符合操作者选择；把所有集成测试塞进无依赖的 Docker build 会混淆构建与环境验证。CI 自动复用本地 NAS 凭据或真实业务数据同样不采用。

## Risks / Trade-offs

- [误把新安装理解为清空旧数据] → 只操作专用空 MySQL schema 和新材料目录，旧路径无写入测试；不附带数据删除任务。
- [新连接池暴露原全局锁掩盖的竞态] → 明确锁序、唯一键、条件转换，真实引擎验证并发领取、全局配额、同身份重认证和死锁失败边界。
- [实例锁连接丢失与旧网络请求竞态] → 停止旧 epoch 调度，结果按原范围保守记账，不承诺撤回或 exactly-once 外部效果，禁止自动接管旧工作。
- [共享 Redis 聊天副本扩大可读范围] → 独立账号/ACL、明确键前缀、TLS 选项、有限 TTL/窗口，禁止密钥进入缓存；拥有 NAS/Redis 管理权限的人仍能读取数据，不作透明加密承诺。
- [缓存 stale、回填覆盖、恢复后旧键重用] → 数据库 revision、原子版本比较、覆盖验证和每次启动新 cache epoch；读取授权不能缓存替代。
- [Redis 网络开销或模型耗时掩盖收益] → 和已优化 SQL 比较，分别测数据库与模型阶段，不声称一定显著缩短整体回复。
- [生产包删除探针后 CI 仍引用旧入口] → 先提供独立诊断构建及新烟测，再退役旧脚本引用，并检查 JAR 内容。
- [旧 change 与本 change 要求重叠] → 本次只写新 change；后续同步/归档前协调部署、存储、缓存前缀与验收状态，不把已失效 SQLite 验收直接复用。

## Migration Plan

1. 实施前核实 MySQL/Redis 实际版本和最小命令/权限集，记录测试兼容矩阵；只读 NAS 检查需单独取得连接授权，不要求操作者公开密码。
2. 操作者准备新的专用 MySQL schema、账号、Redis 键授权和私有材料目录；新版本不访问旧 SQLite 业务，不编写数据导入脚本。
3. 完成新存储、缓存、时间上下文和替代测试后，退役旧生产实现及失效探针引用；通过本地合成微信/模型和显式配置的外部 MySQL/Redis 执行回归与性能验证，不要求独立数据库镜像，报告中保留无法安全执行的待验场景。
4. 在停止旧应用后部署新镜像，配置外部依赖并重新初始化管理员、模型及用户。真实扫码可能影响旧账号 token，必须由操作者在场授权，不并行运行同一微信绑定的旧实例。
5. 验证测试应用重启、应用侧 Redis/MySQL 断连与恢复、第二实例拒绝、用户隔离、时间问答和停止预算；不以停止共享数据库服务制造故障。真实扫码、模型调用和备份恢复按独立授权执行；MySQL 新业务备份在停止唯一应用实例后执行，恢复必须使用兼容版本并重新生成缓存运行命名空间。没有安全恢复目标或覆盖授权时保留恢复场景待验，Redis 不要求备份。
6. 需要回滚时先停止新实例，再使用旧镜像与其原独立 SQLite 目录；MySQL 新产生业务不会反向合并到旧数据库。仅不保留旧账号/聊天的决定不等于授权自动删除旧目录或新 schema。

## Open Questions

- 已核验基线为 MySQL 8.0.44、Redis 7.2.12，Connector/J 9.6.0、HikariCP 6.3.3、Lettuce 6.6.0.RELEASE；命名锁和原子比较基础能力已验，不代表完整业务验收。操作者明确不启用 SSL，沿用本地 MySQL `DISABLED`、Redis `tls: false`，不改变公共模板安全默认值。后续需测量真实网络时延及完整业务兼容性，服务版本变化须重新记录。
- 缓存 TTL、单窗口字节上限、连接池大小和超时的最终值，在合成环境与授权的 NAS 测量后调整；默认值不是服务端资源保证。
- NAS 项目专用资源的建表与合成数据/缓存读写已授权；真实微信/付费模型、覆盖式恢复仍待另外授权。无法安全执行的验收保留未完成，旧 change 的任务状态不因本次规划修订而改变。
