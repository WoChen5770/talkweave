# MySQL / Redis 合成性能报告（2026-09-30）

## 环境与口径

- macOS arm64，Java 21.0.12.1、Maven 3.9.16；真实 MySQL **8.0.46**、Redis **7.4.9**，Connector/J 9.6.0、HikariCP 6.3.3、Lettuce 6.6.0.RELEASE。连接使用操作者填写的私有配置，**MySQL SSL DISABLED、Redis TLS false**。
- 固定合成原始问答，初始已确认历史 100/1000/10000 轮，每个并发用户单独会话，N=20、窗口262144字节、TTL60秒；并发1/4。每组每用户先执行2轮热身，再顺序执行20轮，因此正式样本为20/80，历史逐轮增长且各路径工作量相同。p95 样本量有限，不外推为线上SLA。
- MYSQL=优化的有限 SQL 直读；COLD=每轮前仅删除本测试精确缓存键（预处理不计整轮时间）；HOT=首轮回填后确认送达增量维护；FAILURE=本机受控不响应的 Redis peer，测试预算、旁路与探测，不停止共享 Redis。
- 假模型固定 sleep10ms，实测包含操作系统调度抖动；假发送立即成功，无真实模型/微信请求。整轮从接收持久化开始，经过领取、历史、时间与预算、模型尝试记账、回复保存、发送前复核到确认投递及缓存更新结束。不是仅把“历史时间+10ms”称作整轮。
- 历史阶段单独计时；元数据读取在 Redis 之前结束事务。正文计数为实际回源调用；本次全部正常完成，每次执行一条有限正文 SQL。元数据 SQL 按每次成功授权快照的4条查询计算（用户锁、绑定锁、活动授权范围、事件/会话标记 JOIN），**不包含命名锁/epoch、事务控制、设置或用量 SQL**。
- poolAcquire 为该组连接池获取累计耗时，包含运行和测试簿记，不是服务器 SQL 时间或单次p95。指标无身份/正文/凭据标签。

## 结论

热缓存全部有效命中，正文查询从20/80降为 **0**；从100到10000轮的直读历史p50仍约48–50ms，体现了索引+LIMIT已经有界。Redis冷/故障路径多一次授权快照，故比直接SQL更慢。热缓存仍保留MySQL授权、命名锁与epoch往返，网络与持久阶段主导了整轮耗时，**没有稳定整轮加速**；部分组反而更慢，不报告加速倍数或费用优惠。

收紧预算的对照中，HOT整轮p50略低而p95更高，历史p50/p95也未改善；不能据此宣称调参有效，因此不更改生产100/250ms默认值。若希望进一步改善需另行设计/测量授权查询往返，不能删减权限或所有权校验换取数字。

24组基线共1200个完整测量轮次，调参2组共160轮；全为合成。异常路径模型调用次数与测量轮数相同，没有缓存触发的模型重试。
