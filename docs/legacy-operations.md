# 旧版单用户操作记录（仅用于原镜像回滚）

> 本文不适用于当前多用户镜像。新部署请使用 [多用户 NAS 部署说明](operations.md)。下述手工身份配置与停止窗口仅描述旧版行为，不能用旧程序打开新多用户数据库。

镜像由 GitHub Actions 构建并发布 GHCR，入口见 [github-actions.md](github-actions.md)。NAS 部署、操作和验收由操作者自行执行；无需向代理提供 NAS 凭据。

本轮已用临时目录和合成身份测试登录/配对、代次切换、独立循环、健康状态和停机恢复。下述 NAS 文件管理、目录授权及备份步骤**尚未在操作者 NAS 演练**，任务 7.4/7.5 保持未完成。真实联调凭据不会自动导入正式数据库。

## 1. 准备私有目录和只读配置

- 使用 NAS 本地 ext4/btrfs 等磁盘目录，不把活动 SQLite 放在 SMB/NFS。
- 运行账号默认 UID/GID `10001:10001`；可通过 Compose 的 `ASSISTANT_UID`/`ASSISTANT_GID` 更改。首次启动前由管理员创建数据目录，授予该账号所有权并设置目录 `0700`。仅对自己明确指定的新目录授权，勿递归更改整个共享盘。
- 将 `config.example.yml` 复制为私有 `config/application.yml`，填自己的模型服务及容量；配置文件应由运行账号拥有且 `0600`，Compose 以只读方式挂载。不要把配置、API Key 或配对码发到聊天、提交到代码仓库或嵌入镜像。
- `bot-id` 与 `owner-id` 首次同时留空。两者不同于扫码者 ID，不假定相互等价。配置变更需重启，不提供在线授权或 Web 后台。
- 主程序默认启用运行器，启动后即申请二维码/复用连接；需要纯初始化检查时使用 README 的 `--assistant.enabled=false` 命令。

## 2. 无桌面扫码及配对

在数据目录的 `login/` 查看：

| 文件 | 用途 |
|---|---|
| `status.json` | 当前阶段、challengeId、expiresAt；不含 token/二维码内容 |
| `qr.png` | 当前二维码，仅本地操作者查看，不上传 |
| `verify-code.json` | 服务端要求配对时生成；只填字符串 `code`，保留 challengeId |
| `identity.json` | 绑定挑战或需要人工确认的候选身份 |
| `health.json` | 最近接收循环的脱敏快照，长轮询时可能滞后；健康端点按请求刷新 |

1. 等待 `QR_READY`，查看 `qr.png`，用本人微信扫码。
2. `NEED_PAIRING` 时编辑 `verify-code.json`，例如 `{"challengeId":"保留当前值","code":"微信显示的数字"}`。不要用命令行参数或环境变量传配对码。单次输入上限 2048 字节，仅接受普通文件；不接受符号链接。
3. 当前挑战不匹配、已过期或配对码非法时不向服务端发送。合法提交只消费一次；服务端要求重试时可修正当前文件。不要复用旧挑战。
4. 二维码过期自动清理后重新申请；成功和停止时清理二维码与配对码。`VERIFY_CODE_BLOCKED` / `BOUND_REDIRECT` 停止自动刷新，先核对微信侧提示，再重启重新操作。
5. `PAIRING_INPUT_REJECTED` 时检查文件大小/类型/权限；恢复为当前挑战的正常文件后可继续。不要降低整个数据目录权限来绕过保护。

## 3. 显式绑定（不会信任第一条消息）

1. 未绑定时，打开私有 `identity.json`，读取 `expectedMessage` 中的 `bind-...` 随机挑战，只在你刚扫码的机器人私聊原样发送。
2. 系统只对完整的私聊用户消息核对挑战，不记录其他人的正文或关联令牌，不调用模型。
3. 出现 `CANDIDATE_REQUIRES_CONFIRMATION` 后，在本地确认本人发送记录与候选 `botId`/`ownerId` 对应。`scanUserId` 仅作参考，不能拿它替代 `ownerId`。**若不能可靠确认，保持未绑定。**
4. 把确认的两个身份填写到配置中的 `assistant.wechat.bot-id` / `owner-id`；停止后重启应用，配置才生效。候选文件本身不授予权限。
5. 重新登录到不同机器人时旧绑定不会生效；重新核对候选并改配置。不会向新机器人开放旧身份的历史或借用旧关联令牌发消息。同一机器人重登仍有新的连接代次，旧代次的未处理工作保守中断。

## 4. 状态与停机

- `GET http://127.0.0.1:8081/health/live`：循环存活返回 200；等待扫码、未绑定、断网、模型失败不会单独改变存活判断。
- `/health/ready`：同时显示 connection、login、bound、model、intake、pending、uncertain。没有身份、token、正文或模型地址。不做付费模型探测。
- `model=NOT_CALLED` 明确表示尚未实测模型；配置有效、微信连接/绑定和存储正常时可接受首个请求，不冒称模型已验证。最近一次有效请求失败后显示 `FAILED` 且未就绪，后续成功恢复 `SUCCEEDED`。就绪不会阻止系统接收用户的下一次恢复尝试。
- `RECONNECTING` 使用 1、2、4、8、16、30 秒的封顶退避。明确 `-14` 失效后停止使用旧凭据，回到登录流程。无固定 24 小时强制重登规则。
- `BACKLOG`、`LOW_DISK`、`UNAVAILABLE` 暂停新增轮询，保留最后成功游标。`uncertain` 提醒操作者检查中断/可能已投递的轮次，不自动重复计费或发送。
- 应用默认宽限期 20 秒；Compose 固定应用 20 秒并预留 25 秒停止窗口。先停止领取与接收，允许在途工作结束；最后 20% 窗口取消在途请求并持久分类。停止通知独立最多 2 秒，不等待外部服务无限响应。
- 不确定时先检查微信实际收到的内容，必要时由用户重新发起问题。不要把另一条消息的 context token 拿来人工补发，也不要通过改数据库状态强行重试。

## 5. 备份/恢复（待 NAS 演练）

1. 使用 `docker compose stop assistant` 停止实例并确认进程退出；若被强杀，保留 SQLite 的 WAL/SHM 文件，禁止只复制单个运行中的数据库文件。
2. 备份整个数据目录和单独保护的配置，同时记录应用镜像版本/摘要、数据库结构版本和 UID/GID。备份是包含聊天及凭据的敏感数据，应限制访问并按 NAS 能力加密；不上传到公开仓库。
3. 恢复到一个新的本地目录，保留故障原件，使用兼容版本且只启动一个实例。较新结构会拒绝旧版本直接读取；迁移失败时使用旧镜像和迁移前的一致性备份回滚，不删除故障数据库重建来伪装成功。
4. **旧备份可能落后于远端已执行结果。** 恢复前人工核对未完成轮次和实际微信记录；在核对前不要启用运行器（可以 `assistant.enabled=false` 只检查结构）。确认不会重放已完成的外部操作后才启动。
5. 核对当前会话、聊天历史和中断/不确定状态。备份不能延长微信 token 有效期，明确失效仍需重新扫码及核对绑定。
