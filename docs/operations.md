# 多用户管理端：NAS 部署与恢复

当前是待验收版本。可部署管理端、配置模型和管理用户，但生产扫码身份映射仍保持 `IDENTITY_UNVERIFIED`，尚不能自动开通真实用户。真实两账号协议与 NAS 验收由操作者部署后配合完成，不能用页面可访问或合成测试通过替代。不要替换正在使用的旧实例或挂载其数据目录。

## 1. 独立安装

1. 保存原部署的镜像摘要、Compose、私有配置和完整数据备份。新建独立部署目录，放入当前版本的 `compose.yml` 与 `.env.example`；镜像应选用该提交构建且通过双架构 CI 的确定标签/摘要，而不是假定远端 `latest` 已包含本次改动。
2. 在新部署目录内创建空的 `data-multi-user`，使用 NAS 本地 ext4/btrfs 等磁盘，不用 SMB/NFS 保存活动 SQLite。Compose 禁止自动创建缺失的宿主机挂载路径。
3. 将 `.env.example` 复制为 `.env`，限制为操作者可读（`0600`）。默认运行身份为 `0:0`，数据目录应由 root 拥有并设为 `0700`。可以设置 `ASSISTANT_UID`/`ASSISTANT_GID` 为专用账号，但必须先让该账号拥有这个新目录并能设置私有权限；不要递归修改共享盘。
4. 填入 `ADMIN_INIT_USERNAME` 和唯一强密码 `ADMIN_INIT_PASSWORD`（12–72 个 UTF-8 字节，无控制字符）。没有公共默认密码；`admin` 只是默认用户名。模型 Key、微信 token 不放进 `.env`。初始化秘密仍可被 Docker 管理员读取，不应把环境变量当保险箱。
5. 执行 `docker compose pull`，然后 `docker compose up -d`。无需外部 `application.yml`、模型配置或 bot-id/owner-id。生产入口强制启用 managed profile，不能借旧配置恢复手工授权路径。

默认 `0:0` 创建的文件归 root 所有，普通宿主机用户可能无法读取备份；root 增大服务失陷的影响面，也不能绕过只读挂载、NAS ACL、root squash 或网络文件系统限制。保持只读根文件系统、移除 capabilities 和 no-new-privileges；禁止用 privileged、777、Docker socket 或自动递归 chown 修复权限。

遇到旧数据库、旧 `login/` 或未知布局会拒绝启动，不会迁移、覆盖、删除旧数据。请选择真正的新空目录，不要删除布局标记来强行启动。

## 2. 受保护的管理入口

默认只发布 `127.0.0.1:8680`，健康检查 8081 只在容器回环监听，不发布到宿主机。微信采用出站连接，不需要公网回调。

可以从自己的电脑建立 SSH 隧道：

```sh
ssh -N -L 18680:127.0.0.1:8680 NAS用户名@NAS地址
```

然后浏览器访问 `http://127.0.0.1:18680`。也可将 `ADMIN_BIND_ADDRESS` 设为指定 NAS 内网地址，并通过受控 VPN/HTTPS 入口访问；不使用 `0.0.0.0` 或路由器公网转发作为默认部署。HTTPS 入口设置 `ADMIN_COOKIE_SECURE=true`，HTTP 隧道保持 false；入口应保持浏览器 Origin/Host 一致，不启用任意跨域或盲目信任代理头。

首次登录成功后，从 `.env` 删除 `ADMIN_INIT_PASSWORD`（兼容旧预览变量 `ADMIN_INITIAL_PASSWORD` 也须移除），执行 `docker compose up -d --force-recreate` 清除容器的初始化秘密，再用原密码登录。管理员状态保存在私有数据库，残留初始化参数不会重置密码。不要分享 `docker compose config`、容器 inspect 或环境变量输出，其中可能有秘密。

## 3. 配置与扫码

- 在“全局设置”填写兼容 API 地址、模型名、Key、系统提示词与预算。默认使用 HTTPS；Key 写入后不读回，留空保留已配置值。保存不会发起付费探测，后续新调用使用新版本，在途调用保留原快照。
- 默认会话空闲超时 30 分钟，允许 1–1440 分钟整数，保存后对下一条有效消息生效。超时或 `/new` 开始新上下文但不删除历史、注销微信或影响其他用户；NAS 应保持时间同步。
- 兼容缓存不保证命中或折扣。接口未报告的用量显示未知；缓存输入是输入的子集，不与输入重复相加，也不虚构节省金额。
- 新增用户只建立记录，不产生微信请求。点击“绑定微信”才申请真实二维码；管理员应只将短期二维码展示给预期扫码者。备注名不能证明现实身份，持有码者是邀请信任边界。
- 页面支持扫码进度、配对码、刷新、取消和过期提示；二维码与配对码不要上传、转发为公开邀请或写入日志。目前即使微信确认登录，也会因未验证映射显示“无法确认身份”，不会授予聊天权限。
- 账号接入资格、地区/客户端要求、配对限制及重扫结果以微信实际返回和协议验证为准，不保证所有微信账号可用。真实验证按 [两账号协议步骤](multi-user-protocol.md) 单独授权；同号重扫可能撤销旧凭据。
- 后续生产适配通过验证后，正常开通不需要发送口令、编辑 YAML 或重启。停用/恢复与明确更换身份均在页面完成；重新认证必须是原身份，更换身份不能继承旧历史。

## 4. 停止与诊断

使用 `docker compose stop assistant`。示例不设置 `stop_grace_period`，不再带旧版 20 秒命令；Web 每阶段等待设为 1 秒，运行调度器取消后最多等 4 秒。完整应用目标为 8 秒内收尾，存储异常或外部操作不确定须保留诊断，不通过重发模型请求补状态。完整带在途请求停机及 NAS 实测仍需验收，不能仅凭默认参数宣称通过。

内部 `/health/live` 不因单用户待扫码或模型失败而失效；`/health/ready` 可报告全局容量、磁盘或数据库问题。不要为某个用户暂时未就绪配置反复重启。数据目录或数据库错误应修复存储条件，不删除数据库“重试”。

## 5. 停机备份、恢复与回滚

1. 停止实例并确认容器已退出；备份整个新数据目录，包括 `managed-layout`、数据库、仍存在的 WAL/SHM、锁和受保护材料，以及 Compose、私有 `.env` 和可选运维配置。不能只复制正在写入的 SQLite 主文件。
2. 记录镜像 manifest 摘要、布局版本、NAS 架构、备份时间及 UID/GID。备份含管理员哈希、聊天、模型 Key 和微信凭据，应保留所有权/`0700`、`0600` 权限，限制读取并加密保存，不提交仓库。
3. 恢复到另一个独立目录，保留故障原件。使用与该布局兼容的镜像，更新挂载路径和匹配的 UID/GID；任何时刻只允许一个实例占用该目录。
4. 旧备份可能落后于远端已执行结果。恢复含有效绑定的数据会恢复后台连接；先在隔离出站网络的环境中核对备份时间和未完成操作，确认风险后再恢复联网。已记录的不确定模型/投递不得手改状态重放或重复计费。
5. 登录核对管理员、用户、绑定状态、会话活动时间及已知/未知用量。临时二维码重启后失效；备份不能延长远端凭据寿命，必要时原身份重新认证。
6. 回滚旧单用户版本时，停止新实例，使用原旧镜像和原独立目录/一致性备份；绝不能用旧程序打开新库，也不把“不迁移”解释为删除旧数据。重复扫码可能已让旧 token 失效，本地回滚不能恢复远端授权，可能仍需重新登录。
